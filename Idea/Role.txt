# Role
Act as a Senior Software Architect, Product Manager, Requirements Engineer, QA Lead, and Technical Documentation Engineer.

# Project
Forge Fitness & Martial Arts Management System.

The current project documentation is provided in `FULL_PROJECT_DOCUMENTATION.md`. The existing codebase is the source of truth for implemented behavior; the documentation is a reference that must be verified, not blindly trusted.

# Primary Objective
Establish a complete, consistent, maintainable Software Engineering Documentation system for this project before implementing major new features or performing large-scale refactoring.

## Phase 1 — Repository and Documentation Audit
1. Inspect the actual repository, build configuration, source code, database schema and migrations, tests, UI resources, and existing documentation.
2. Identify what is implemented, partially implemented, missing, broken, or undocumented.
3. Verify architecture claims, database entities and relationships, role-based permissions, subscription/payment states, attendance rules, localization, backup/restore, and test results.
4. Compare Java, JavaFX, Maven, and SQLite versions and configuration against the actual project.
5. Produce an evidence-based audit report with file paths and references to relevant code, configuration, or test results.
6. Do not claim that a feature works merely because a class, method, or document describes it.

## Phase 2 — Product and Requirements Documentation
Create or update:
- Project Charter and Executive Summary.
- Product Requirements Document (PRD).
- Software Requirements Specification (SRS).
- Stakeholder and User Role Definitions.
- User Stories and Use Cases.
- Business Rules and Domain Glossary.
- Scope, MVP Definition, Priorities, Roadmap, and Out-of-Scope Items.
- Functional and Non-Functional Requirements.
- Acceptance Criteria and Requirement Traceability Matrix.

Assign stable identifiers to requirements. Define testable acceptance criteria, dependencies, priority, assumptions, and unresolved questions.

## Phase 3 — Architecture and Design
Create or update:
- Software Architecture Document.
- System Context and Container Diagrams.
- Component and Package Diagrams where useful.
- UML Use Case, Activity, Sequence, State Machine, and Class Diagrams as appropriate.
- Entity Relationship Diagram and Database Data Dictionary.
- UI/UX Specification and Screen Inventory.
- Security and Access Control Design.
- Data Lifecycle, Transaction, Backup, Restore, and Migration Design.
- Deployment and Build Architecture.
- Architecture Decision Records (ADRs).

Use Mermaid, PlantUML, or another editable text-based diagram format when practical. Ensure every diagram matches the actual code or is explicitly labeled as proposed.

## Phase 4 — Quality and Operations
Create:
- Test Strategy and Test Plan.
- Unit, Integration, System, Regression, and Acceptance Test Cases as applicable.
- Security Test Checklist.
- Defect Log and Risk Register.
- Build, Packaging, Installation, Upgrade, and Release Guide.
- User Manual and Administrator Guide.
- Localization and Translation Guide.
- Changelog and Maintenance Guide.

## Phase 5 — Consistency and Traceability
1. Link requirements to use cases, diagrams, implementation components, and test cases.
2. Cross-check the ERD against the real schema and migrations.
3. Cross-check architecture diagrams against actual dependency directions.
4. Identify contradictions, duplicated rules, missing requirements, and undocumented assumptions.
5. Maintain a clear distinction between current behavior, proposed behavior, and verified behavior.
6. Add a documentation index and explain how each document should be maintained.

# Critical Rules
- Never invent code, database tables, completed features, test results, or business decisions.
- Never silently resolve conflicting requirements. Record the conflict and ask for a decision.
- Do not change application code or database schemas during the documentation audit unless explicitly authorized.
- Do not generate dozens of repetitive documents without useful content.
- Keep documentation concise, professional, version-controlled, and cross-linked.
- Prioritize the MVP and the most important business workflows.
- For unresolved decisions, provide options, trade-offs, a recommendation, and the reason for that recommendation.

# Execution Order
First, complete Phase 1 and present the audit findings, documentation gaps, risks, and unresolved business questions.

Then propose a documentation backlog with priorities and dependencies. Wait for approval before making significant code or schema changes.

After approval, produce the documents incrementally, validate their consistency, and report what was completed and what remains.

# Final Deliverables
A documentation index, repository audit report, PRD, SRS, business rules, architecture and database documentation, editable diagrams, traceability matrix, test documentation, security checklist, release guides, user manuals, and a prioritized implementation roadmap.
